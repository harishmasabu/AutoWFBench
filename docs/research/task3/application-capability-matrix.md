# Sapiens4 application capability matrix

**Confirmed architecture direction:** simApp-first for every selected application, even where APIs exist. A simApp supplies the full simulated UI needed by the selected workflow, over authoritative local state. simMCP is a later optional optimization when the application has adequate MCP capabilities; unavailable or limited MCP leaves the UI primary. API/CLI findings below document semantics and feasibility, not permission to substitute an API-first benchmark. See [decisions and roadmap](../decisions-and-roadmap.md).

Verification date: 11 October 2026. This is documentation research, not authenticated integration testing. No customer accounts were connected. Workflow IDs refer to [application inventory](application-inventory.md). An illustrative brand is a proposed implementation choice.

**VERIFIED (V):** the cited primary documentation explicitly supports the stated capability. **PARTIALLY VERIFIED (P):** interface existence is supported but required operation coverage, access eligibility, or current restrictions remain incomplete. **UNKNOWN (U):** not established by the inspected sources. “U CLI/MCP” means no suitable official interface was established, not proof that none exists. Where a component is P or U, the whole application's end-to-end workflow feasibility remains P or U even if its API exists.

Simulation classifications: **A** faithfully represent a documented official contract (or reuse an offline tool with a proven local endpoint); **B** internal simulated API/CLI for business capability without committing to a vendor contract; **C** simulated UI required by a selected UI interaction; **D** hybrid of documented APIs and UI/physical/external events; **E** unresolved contract. All classifications mean isolated local execution, never live SaaS calls in benchmark runs. An A operation still needs a local stateful implementation; it does not make the live service deterministic.

## Common evidence and boundaries

**G1 — Workspace MCP:** [Google configuration](https://developers.google.com/workspace/guides/configure-mcp-servers) verifies dedicated remote servers and developer-preview membership, enabled APIs, OAuth, and inherited permissions. It does not establish complete REST parity. In particular, Calendar configuration lists read/free-busy scopes; do not infer event-write support from the presence of a server.

**G2 — Workspace CLI:** [googleworkspace/cli](https://github.com/googleworkspace/cli) supplies discovery-driven commands and structured output, but explicitly disclaims official product support and warns of breaking changes. Classify it as a vendor-organization project, pin it if ever adopted, and verify discovery/auth/API endpoint redirection before offline reuse. These interfaces can inform internal semantics; they do not replace the primary simApp UI. No package installation was performed.

**Historical survey interpretation, not execution policy:** For all rows, “no UI required” applies only to the documented selected operations. Account setup, proprietary editing, portal-only actions, personal-account history and uncommon formats may still require UI; those are E until investigated. The current simApp-first policy applies even to operations with APIs. No operation is excused from primary UI coverage by the historical assessment.

**No universal idempotency promise:** AutoWFBench currently requires keys for its own write contract. Provider APIs differ. Preserve only documented provider idempotency/version constraints in a branded facade. Where a provider lacks an idempotency key, test reconciliation using stable business identifiers, readback, and safe retry handling rather than granting free deduplication.

**Blocked evidence:** Meta pages returned fetch/internal/429 errors. QBO entity documentation returned a sparse shell. The linked HubSpot local-development overview failed retrieval; its developer CLI role is corroborated by the earlier official developer-MCP documentation, but CLI business-operation coverage remains partial. These limitations explain P labels; they are not evidence that the APIs are unavailable. Current Meta pricing, limits and personal/group access must be checked before freezing a branded scenario.

## Recommended capability ordering

Implement the Google Drive folder-creation simApp first, including an accessible UI and authoritative outcome checks. Use workflow-relevant message, file/ACL, tabular register and task/CRM contracts to guide subsequent simApp domain models. Scheduling and agreement-signature events follow. Add ledgers and commerce only with explicit authoritative payment, receipt and inspection states. Canva/social publishing, private Recruiter access, domain renewal writes and payroll imports have more access uncertainty or narrower workflow relevance and should not block the common core.

The matrix does not establish market frequency or choose the final top-ten scenarios. Those remain separate tasks.
